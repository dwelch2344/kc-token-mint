# Keycloak Realm-Signed Token Minting Service

## Proposal

A Keycloak extension that exposes a custom REST endpoint per realm for minting arbitrary JWT tokens signed with the realm's active signing key. Tokens are stateless, validate against the realm's standard JWKS endpoint, and contain a discriminated-union payload structure controlled by scope-based authorization and remotely-fetched schema validation.

This is credential minting as a service: callers prove they're allowed to mint a particular *type* of token, supply a payload matching that type's published schema, and receive a signed JWT.

## Token Structure

Every minted token contains:

**Standard claims** (set by the service, not the caller):
- `iss` — realm issuer URL
- `iat` — issued-at timestamp
- `exp` — expiration (caller-requested, clamped by per-type max TTL)
- `jti` — unique token ID
- `aud` — audience (caller-supplied, validated against per-type allowlist)
- `azp` — the calling client's ID (for audit/traceability)

**Discriminator + payload**:
- `type` — string identifying the token type (e.g., `"capability"`, `"event-envelope"`)
- `<type>` — a claim with the same name as the `type` value, containing the caller-supplied payload object

Example minted token (decoded):

```json
{
  "iss": "https://auth.example.com/realms/main",
  "iat": 1735000000,
  "exp": 1735000300,
  "jti": "01HQXY...",
  "aud": "downstream-service",
  "azp": "minter-service-account",
  "type": "capability",
  "capability": {
    "resource": "orders",
    "operations": ["read", "write"]
  }
}
```

Downstream consumers verify the signature via JWKS, then dispatch on `type` to find the payload at the matching claim key.

## Authorization Model

Two-layer check, both required:

**Layer 1 — Role gate.** The caller's access token must contain the realm role `token-minter`. Without it: 403 at the endpoint entry. This is the coarse "is this client allowed to mint at all" check.

**Layer 2 — Scope gate.** The caller's token must include a scope of the form `mint:<type>` for the requested type. Each mintable type corresponds to a Keycloak client scope. Scope assignment uses Keycloak's existing mechanisms — no custom admin UI needed.

This separation means a single role grants endpoint access, while individual scopes grant per-type permission. Adding a new mintable type means creating a client scope and assigning it to authorized clients.

## Per-Type Configuration

Each `mint:<type>` client scope carries attributes that configure its behavior:

| Attribute | Purpose | Required |
|---|---|---|
| `schema-uri` | URL where the payload schema is fetched | Yes |
| `schema-content-type` | Overrides response Content-Type from the fetch | No |
| `max-ttl-seconds` | Upper bound on token lifetime | Yes |
| `allowed-audiences` | Comma-separated list of valid `aud` values | Yes |

Configuration lives on the scope, not in code, so adding/modifying types is an admin operation.

## Schema Fetching

When a mint request arrives, the service fetches the schema from `schema-uri`. Behavior:

- **Content-Type resolution.** If the scope has `schema-content-type` set, use it. Otherwise read it from the HTTP response's `Content-Type` header. If neither is present: reject the request.
- **Supported content types initially.** `application/schema+json` and `application/json` are treated as JSON Schema. The content-type field is forward-looking — additional validators (e.g., CUE, Protobuf descriptors) can be plugged in later.
- **Caching.** Schemas are cached in-process with a TTL (default 5 minutes) keyed by URI. ETag/Last-Modified are honored on revalidation. Cache size is bounded.
- **Fetch timeouts.** Connect and read timeouts are short (2s / 5s default). On fetch failure, fall back to the last successfully cached schema if one exists and is within a configurable staleness window; otherwise reject with 503.
- **Allowed schemes.** Only `https://` is allowed by default. An optional realm-level attribute can permit `http://` for development.
- **SSRF protection.** Schema URIs are checked against a denylist of private/loopback/link-local ranges unless a realm-level override permits them.

## Request and Response

**Request:**

```
POST /realms/{realm}/mint/token
Authorization: Bearer <caller's access token>
Content-Type: application/json

{
  "type": "capability",
  "payload": { "resource": "orders", "operations": ["read"] },
  "ttl_seconds": 300,
  "audience": "downstream-service"
}
```

**Response (success):**

```json
{
  "token": "eyJhbGciOi...",
  "expires_at": 1735000300,
  "jti": "01HQXY..."
}
```

**Response (error):** Standard JSON error body with `error` and `error_description`, mapped to appropriate HTTP status codes (400 for validation, 401 for missing/invalid bearer, 403 for authorization, 422 for schema validation failure, 503 for schema fetch failure).

## Validation Pipeline

For each request, in order — any failure short-circuits with the appropriate status:

1. Bearer token present and valid → else 401
2. Caller token contains `token-minter` realm role → else 403
3. `type` field present and matches `^[a-z][a-z0-9_-]*$` → else 400
4. `type` is not in the reserved set (`iss`, `sub`, `aud`, `exp`, `iat`, `nbf`, `jti`, `azp`, `act`, `scope`, `type`) → else 400
5. Caller token contains `mint:<type>` scope → else 403
6. Load client scope, read configuration attributes → else 500 (misconfiguration)
7. `ttl_seconds` is positive and ≤ scope's `max-ttl-seconds` → else 400
8. `audience` is in scope's `allowed-audiences` → else 403
9. Payload serialized size ≤ 4KB, nesting depth ≤ 8 → else 400
10. Fetch schema (with caching/fallback as described) → else 503
11. Validate payload against schema → else 422
12. Build JWT, sign with realm's active key, emit audit event, return

## Audit Logging

Each mint attempt emits a Keycloak event via `EventBuilder`:

- `EVENT_TYPE`: `CUSTOM_MINT` (or success/failure variant)
- Includes: caller's client ID, requested type, requested audience, requested TTL, resulting `jti` (on success), error code (on failure)
- Does **not** include: the payload contents (could be sensitive)

This flows through Keycloak's existing event store and any configured event listeners.

### Factory and Provider

`MintResourceProviderFactory` registers the extension and produces providers per session. `getId()` returns `"mint"`, which makes the endpoint live at `/realms/{realm}/mint/...`. The factory holds long-lived resources (HTTP client, schema cache, validator instances) initialized in `postInit`.

`MintResourceProvider` is per-session, returns the JAX-RS resource from `getResource()`, and closes per-session resources in `close()`.

### MintResource

The JAX-RS resource holds a reference to `KeycloakSession` and the factory's shared components. It exposes one method:

```
@POST @Path("token")
@Consumes(MediaType.APPLICATION_JSON)
@Produces(MediaType.APPLICATION_JSON)
public Response mint(MintRequest request)
```

The method runs the validation pipeline. Each step that can fail returns early with an error response. Authentication uses `AppAuthManager.BearerTokenAuthenticator` against the current realm.

### TypeConfigLoader

Given a `type` string and the current realm, finds the client scope named `mint:<type>`, reads its attributes, and returns a `TypeConfig` record:

```
record TypeConfig(
    String type,
    URI schemaUri,
    Optional<String> schemaContentTypeOverride,
    Duration maxTtl,
    Set<String> allowedAudiences
)
```

Returns `Optional.empty()` if no such scope exists. The check for whether the caller is *assigned* the scope is separate — it reads `scope` from the caller's access token.

### SchemaFetcher and SchemaCache

`SchemaCache` wraps Caffeine with TTL-based expiry and tracks ETag/Last-Modified per entry. `SchemaFetcher` uses Java 11+ `HttpClient` with configured timeouts. The fetcher:

1. Checks cache; if fresh, returns
2. If stale or missing, performs conditional GET using stored validators
3. On 304, refreshes cache freshness and returns cached
4. On 200, validates content-type (respecting scope override), parses, stores, returns
5. On failure, returns last-known-good if within staleness window, else throws

A `SchemaFetchException` carries enough detail for the resource to decide between 503 (transient) and 500 (misconfiguration).

### PayloadValidator

An interface:

```
interface PayloadValidator {
    ValidationResult validate(JsonNode payload, FetchedSchema schema);
    boolean supports(String contentType);
}
```

`JsonSchemaPayloadValidator` handles `application/schema+json` and `application/json`. The factory holds a list of validators and dispatches by content type. Additional implementations can be added without touching the resource code.

### TokenBuilder

Encapsulates JWT construction:

```
class TokenBuilder {
    String build(
        RealmModel realm,
        KeycloakSession session,
        String callerClientId,
        String type,
        JsonNode payload,
        String audience,
        Duration ttl
    );
}
```

Uses `session.keys().getActiveKey(realm, KeyUse.SIG, Algorithm.RS256)` to retrieve the signing key, builds a `JsonWebToken`, sets the discriminator and payload as additional claims via `setOtherClaims`, then signs with `JWSBuilder`. The algorithm is selected based on the realm's active key type (RS256/ES256/etc.) rather than hardcoded.

### MintEventLogger

Wraps `EventBuilder` setup with a small fluent API so the resource code doesn't have to repeat field-setting on every code path. Success and failure paths both flow through it.

### Configuration knobs (SPI config)

The factory accepts SPI configuration for operational tuning:

```
spi-realm-restapi-extension-mint-schema-cache-ttl-seconds=300
spi-realm-restapi-extension-mint-schema-cache-max-size=1000
spi-realm-restapi-extension-mint-schema-fetch-connect-timeout-ms=2000
spi-realm-restapi-extension-mint-schema-fetch-read-timeout-ms=5000
spi-realm-restapi-extension-mint-schema-staleness-window-seconds=3600
spi-realm-restapi-extension-mint-allow-http-schemas=false
spi-realm-restapi-extension-mint-allow-private-ip-schemas=false
```

These get loaded via `Config.Scope` in the factory's `init` method.

## Deployment

Build as a JAR, drop into `providers/` directory of the Keycloak distribution, run `kc.sh build` to rebuild the augmented distribution, then start normally. The endpoint becomes available at `/realms/{realm}/mint/token` for any realm.

Operational setup per realm:

1. Create realm role `token-minter`
2. Assign role to service accounts of clients that should mint
3. For each token type:
   - Publish the schema at a stable HTTPS URL
   - Create a client scope named `mint:<type>` with attributes: `schema-uri`, `max-ttl-seconds`, `allowed-audiences`
   - Optionally set `schema-content-type` to override response headers
   - Assign the scope to clients that should mint that type

## Open Questions for Implementation

- **Schema content-type for non-JSON.** Initial implementation is JSON Schema only. The `schema-content-type` field is wired through, but additional `PayloadValidator` implementations are deferred until needed.
- **Per-type rate limiting.** Not in v1. If abuse becomes a concern, the natural place is a separate filter keyed by `(client_id, type)`.
- **Key rotation behavior.** Tokens are signed with whatever's the active key at mint time and include a `kid`. No special handling needed — standard JWKS rotation applies.
